Fix 1: Reconcile-on-transaction logic for the "Remaining this month" calculation (items 1+2)
The bug:
When the Hari Gaji banner creates a debt repayment transaction, the user's debt is now subtracted twice from "Remaining this month":

Once because debts.monthly_payment is summed into the planned-outflows side of Remaining
Once because the actual transaction is summed into actual-outflows side of Remaining

The fix — Option A: Reconcile on transaction
When a transaction is linked to a planned debt, the planned amount stops being subtracted from Remaining. The transaction takes its place.
Step 1.1 — Add a link between transactions and debts
Add a column to the transactions table:
linked_debt_id  uuid (nullable, foreign key → debts.id)
This column establishes a 1-to-1 link from a transaction to the debt it pays off.
Step 1.2 — Auto-link Hari Gaji-created debt transactions
When the user confirms the Hari Gaji review modal and the system creates debt repayment transactions, each transaction must be created with linked_debt_id set to the corresponding debt's ID.
Income transactions (salary) do NOT need this column — leave linked_debt_id = null for income.
Find the existing Hari Gaji confirmation handler (creates transactions in batch). Modify it so that for each debt-repayment line item, the resulting transaction includes linked_debt_id.
Step 1.3 — Modify the "Remaining this month" calculation
Locate the function/query that computes "Remaining this month" on the Dashboard.
Current logic (broken):
remaining = salary
          - SUM(commitments.monthly_amount)
          - SUM(debts.monthly_payment)         ← subtracted as planned
          - SUM(transactions for current month) ← also subtracted as actual (DOUBLE COUNT)
New logic (correct):
// For each debt, check if a transaction has reconciled it this month
reconciled_debt_ids = SET of debt IDs where there exists a transaction for the current month with linked_debt_id matching that debt

unreconciled_debts_total = SUM(debts.monthly_payment) WHERE debt.id NOT IN reconciled_debt_ids

remaining = salary
          - SUM(commitments.monthly_amount)
          - unreconciled_debts_total           ← only debts NOT yet transacted
          - SUM(transactions for current month) ← all actual outflows
Key insight: a debt's monthly_payment is subtracted from Remaining UNTIL a transaction with linked_debt_id referencing it appears for the current month. After that, only the actual transaction amount counts.
V1 limitation (acceptable): Manually-created transactions do NOT auto-link to debts. Only Hari Gaji-created transactions reconcile. We accept this limitation for v1 and may add manual linking in a future milestone if users request it.
Step 1.4 — Verify other Dashboard KPIs are not affected
The KPI cards "Salary", "Fixed Commitments", "Liabilities", "Total Spent" should not change. Only "Remaining" calculation changes. Verify before reporting complete.

Fix 2: Hari Gaji should not fire on or before onboarding day (item 9)
The bug:
When a user completes onboarding and their payday for the current month has already passed (or is today), the Hari Gaji banner fires immediately. The user can confirm "Yes I got paid" and the app creates a salary income transaction + debt repayment transactions on top of account balances that already reflect those events.
Why it's wrong: Account balances entered during onboarding represent the user's CURRENT state — already post-salary, already post-debt-deductions for the current month. Adding new transactions for events that already happened double-counts everything.
The fix:
Modify the Hari Gaji banner trigger logic. Add this rule to the existing logic:
SKIP the banner for the current month if:
  current_month_payday_date <= user.onboarded_at
Where:

current_month_payday_date = a date object built from current year + current month + user's payday (day-of-month)
user.onboarded_at = a timestamp recorded when the user completed onboarding

Step 2.1 — Add onboarded_at to user model if not already present
Check the user table schema. If onboarded_at doesn't exist, add it:
onboarded_at  timestamp (nullable)
Set it to NOW() when a user completes the final step of onboarding.
For existing users who already completed onboarding before this column existed, backfill onboarded_at = created_at (a reasonable approximation).
Step 2.2 — Update the banner trigger logic
Find the function that decides whether to render the Hari Gaji banner (likely in GET /api/payday-prompt/current from Phase 3.3). Add the new skip condition.
Pseudocode:
function shouldShowPaydayBanner(user):
  if user.payday is null or user.monthlyIncome is null:
    return null  # existing rule

  today = today's date
  current_month_payday_date = construct(today.year, today.month, user.payday)

  # NEW RULE
  if current_month_payday_date <= user.onboarded_at:
    return null  # current month's payday already passed at onboarding time

  # existing rules continue (check today >= payday, check pending state, etc.)
  ...
Step 2.3 — Edge cases to handle

Payday=31 in a 30-day month: existing logic should treat as "last day of month". Verify still works after this change.
Existing users with no onboarded_at after backfill: created_at is the fallback. Users created before this fix would have onboarded_at = created_at, which is correct because their first payday after the column was added still passes this rule.
User changes their payday mid-month: the rule still applies based on the new payday value. If they change payday from 25 to 1 mid-month, and onboarded_at was last week, the new payday=1 has already passed for the current month → banner skipped. Acceptable behavior.
