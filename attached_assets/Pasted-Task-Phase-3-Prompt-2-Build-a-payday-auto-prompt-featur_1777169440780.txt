Task: Phase 3 Prompt 2 — Build a payday auto-prompt feature with in-app banner only (no email, no push)
When a user's configured payday arrives, the app proactively prompts them to confirm receipt of salary and auto-create the income transaction plus their debt repayment outflows. This reduces friction in monthly money management and increases data quality (more transactions logged).
This is v1 — banner-only. Email reminders and web push notifications are explicitly out of scope and will be added in later phases (3.3b and 3.3c respectively).
Read these files first to understand existing conventions:

The user model / schema (look for payday, monthlyIncome, salary-related fields)
The Debts page and debt model (looking for monthly_payment field)
The Transactions API (how transactions get created)
src/i18n/locales/en.json, ms.json, id.json (for established terminology)
Existing banner/notification components if any


What we're building
A persistent in-app banner that appears at the top of every page when:

Today's date matches the user's configured payday day-of-month, AND
The user has an active record indicating they haven't yet acted on this month's prompt

When the user clicks "Yes, I got paid", a review screen opens showing proposed salary income + debt repayment transactions. User can edit, deselect, and confirm. On confirmation, all selected transactions are batch-created.

Step 1: Database schema — payday prompt lifecycle table
Create a new table payday_prompts:
id                  uuid (primary key)
user_id             uuid (foreign key)
year                integer (e.g., 2026)
month               integer (1-12)
state               enum ('pending', 'confirmed', 'skipped', 'remind_tomorrow')
remind_after_date   date (nullable, used for 'remind_tomorrow')
confirmed_at        timestamp (nullable)
created_at          timestamp
updated_at          timestamp

Unique constraint: (user_id, year, month)
When a user's payday arrives and they have no record for that month, the system creates a pending row. State transitions:

User clicks "Yes, paid" + confirms transactions → confirmed
User clicks "Skip this month" → skipped
User clicks "Not yet, remind tomorrow" → remind_tomorrow with remind_after_date = today

The next time the user opens the app:

If state is pending and today is on or after their payday → show banner
If state is remind_tomorrow and today > remind_after_date → show banner (revert to pending behavior)
If state is confirmed or skipped → no banner
Once month rolls over and there's no record for the new month → create new pending row when user's payday arrives


Step 2: Backend API endpoints
Create these endpoints:

GET /api/payday-prompt/current — returns the active prompt for the user (or null if none)

Response: { id, state, year, month, payday: number, monthlyIncome: number, debts: Debt[] }
Logic: find or create the appropriate payday_prompts row based on today's date and user's payday. Return null if no banner should show.


POST /api/payday-prompt/:id/confirm — confirms the prompt and creates transactions

Body: { transactions: [{ type: 'income' | 'debt_payment', amount, accountId, debtId?, date, description }] }
Logic: create each transaction in user's account. Update prompt state to confirmed. Return success.


POST /api/payday-prompt/:id/skip — marks as skipped for this month
POST /api/payday-prompt/:id/remind-tomorrow — marks as remind_tomorrow


Step 3: The Banner component
Create src/components/PaydayBanner.tsx. Renders at the top of the app's authenticated layout (above all pages).
Visual design:

Full-width banner, brand green background or subtle accent
Wallet/calendar icon on the left
Text: "Hari Gaji! Did you receive your salary today?" (translated per locale)
Three buttons on the right: "Yes, I got paid" (primary), "Not yet" (secondary), "Skip this month" (subtle/text-only)
Mobile responsive — stacks vertically on small screens

Behavior:

On mount, hits GET /api/payday-prompt/current to check if it should render
If response is null, banner doesn't render
"Yes, I got paid" → opens the Review modal (Step 4)
"Not yet" → POST /api/payday-prompt/:id/remind-tomorrow → banner hides until tomorrow
"Skip this month" → POST /api/payday-prompt/:id/skip → banner hides until next payday cycle

Persistence:

Banner state should refresh when user navigates between pages
Should re-check on app boot
No need for real-time updates — banner state changes on user action

Step 6: Edge cases to handle

User has no debts: modal still works, just income line only with helpful message: "No active debts to pay this month."
User has no monthlyIncome configured: banner doesn't show, OR shows but Yes button leads to a Settings prompt: "Please configure your salary in Settings first."
User has no payday configured: banner doesn't show. Add this to the audit — make sure payday is required in onboarding (existing functionality, just verify).
Payday on 31st in a 30-day month: if user's payday is 31, treat it as "last day of month" for months without a 31st (so Feb users with payday=31 get prompted on Feb 28/29, April users get prompted on April 30, etc.). Don't skip the month entirely.
User changes payday mid-month: existing prompt stays valid for current month. New payday applies starting next month.
User confirms with deselected debts: only selected items get created. Deselected items are NOT carried forward — they're skipped for this month. User can manually add them later if needed.
